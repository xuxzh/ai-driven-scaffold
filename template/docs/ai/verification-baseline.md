# 验证基线

> **这是单点定义文件**。所有验证强度的收敛都按此文件分层；不指定具体命令，由各项目在 AGENTS.md 补全实际命令。

## TL;DR

- **4 档验证**：`minimal`（`L0` 最窄检查）/ `l1`（受影响层）/ `fast`（主链路快速）/ `full`（lint → typecheck → test → build）。
- **AI 必跑（硬门禁）**：`L1+` 完成前必须跑 `verify` 并写入 `## 验证证据`；缺证据视为未完成（[ADR-0002](../adr/0002-verify-hard-gate.md)）。
- **CI 是验证层不是准入层**：CI 跑 verify 加固纪律，不替代人工批准。

## 核心原则

按风险等级分层收敛，不要求所有改动都跑完整基线。选择验证的两条原则：

1. **必须足以暴露改动引入的回归**
2. **不应跑明显与当前切片无关的命令**（防止"全量跑一遍"造成的成本与噪声）

## 分层验证基线

| 级别 | 验证要求 |
|---|---|
| `L0` | 至少执行一个与改动直接相关的最小验证 |
| `L1` | 验证被修改的那一层（相关测试 + 局部 lint 或 typecheck） |
| `L2` | 覆盖静态检查、类型检查和受影响功能测试；主链路变化时补 E2E |
| `L3` | 在完整基线外，再人工确认验证范围是否足够 |

## 合并前验证强度（按改动类型）

| 改动类型 | 验证要求 |
|---|---|
| 纯文档改动 | 文档自检、占位符扫描、Git 状态确认；不要求运行完整验证 |
| 代码改动 | 运行与改动直接相关的单元测试，并按影响面补充 typecheck 和 lint |
| 工具链、依赖、构建、CI 或环境配置改动 | 运行完整验证，或在有明确原因时运行覆盖同等风险面的替代命令 |
| 验证失败且失败点与 diff 无关 | 标注为基线失败，说明失败文件和命令，由用户决定是否继续合并或先修复基线 |

## 默认完整基线

各项目**必须**在根级 package/manifest 中定义一个 `verify` 命令，串联以下步骤：

1. 静态检查（lint）
2. 类型检查（typecheck；如不适用可省略）
3. 单元测试（test）
4. 端到端测试（test:e2e；如不适用可省略）
5. 构建（build）

具体命令由各项目按所选包管理器与构建工具决定，示例：

```text
<pm> lint
<pm> typecheck
<pm> test
<pm> test:e2e
<pm> build
```

其中 `<pm>` 是当前项目实际使用的包管理器（如 pnpm / npm / yarn / uv / cargo / go），**必须**在 `AGENTS.md` 顶部"用户项目元信息"段落中标注。

## AI 必跑（硬门禁）

L1+ 任务在汇报"完成"之前**必须**运行项目根目录的 `verify` 入口（详见 [ADR-0002](../adr/0002-verify-hard-gate.md)）：

- **必须**运行命令
- **必须**在汇报中列出实际退出码与关键输出摘要
- **必须**显式标注未跑项及原因
- 缺信号时任务**不能**被声明完成

`L0` 任务仍按"至少一个与改动直接相关的最小验证"执行；本硬门禁不向下传递到 L0。

## Verification Profile（验证档位）

`verify` 入口从"是否存在"升级为分层语义。Adoption Profile 在 `AGENTS.md` 顶部"用户项目元信息"段登记 4 个验证入口字段，对应 4 档；每档映射到一个最小风险等级 + 对应任务等级的必跑档位：

| 档位 | 字段名（AGENTS.md Adoption Profile） | 适用任务等级 | 验证覆盖 | 必填性 |
|---|---|---|---|---|
| `minimal` | 最小验证入口 | `L0` | 与改动直接相关的最窄检查（单个测试 / 单个 lint / 单个 typecheck） | 必填 |
| `l1` | L1 验证入口 | `L1` | 被修改的那一层（相关测试 + 局部 lint 或 typecheck） | 可选 |
| `fast` | 快速验证入口 | `L2` 无主链路 / 构建风险（如纯文档、纯测试、纯规则文件改动） | 受影响模块的测试 + lint + typecheck | 可选 |
| `full` | 完整验证入口 | `L2` 触及主链路 / 数据流 / 入口 / 构建 / 跨文件行为；`L3` 必填 | lint → typecheck → test → test:e2e（可选）→ build | 必填 |

补充规则：

- `full` 必须**显式**串联 lint / typecheck / test / build（或项目声明的等价风险面）；不得退化为单条 `pnpm test`
- 不适用的档位允许填"无 / N/A"，但**必须**在 Adoption Profile 单元的"你的项目值"列写明"不适用 + 理由"（如"无 e2e 测试，理由：纯文档仓库"）；仅留空仍视为缺字段
- `L3` 任务在 `full` 之上还需**人工专项确认**验证范围是否足够（详见 [task-levels.md](./task-levels.md) 的 L3 段）；该人工确认不通过 AGENTS.md 字段表达，但必须在 `## 验证证据` 段显式落字
- 跨项目差异由 Adoption Profile 字段映射：同一档位在不同项目对应不同命令，但档位语义（覆盖范围、必填性）由本文件统一约束

未跑项处理规则：

- 任一档位实际未跑时，**必须**在 verify 报告 / `## 验证证据` 段显式标注：`未跑项 = <档位>: <原因>`；缺标注视为"已跑但未报告"，按未跑处理（详见 [ADR-0002](../adr/0002-verify-hard-gate.md)）
- "环境限制无法跑 verify"也必须按"未跑项"规则显式标注；不允许把缺失验证包装成成功

## CI 是验证层（不是准入层）

CI 在本治理中属于**验证层**——它的作用是加固 verify 必跑纪律，**不**是准入层的强制门禁。

- CI 模板（GitHub Actions / GitLab CI）可在阶段 0 接入，用于"verify 跑过 / 失败"的事实记录
- CI 跑出的结果可作为 verify 报告的"事实证据"；本 ADR-0002 的"AI 必跑"可降为"AI 必须引用 CI 报告"
- CI **不**替代 ADR-0005 的 L3 Pre-Implementation Approval Gate（这是**准入**而非验证）

## 验证证据的记录位置

- 任务完成时：在 PR/MR 描述或会话汇报中列出实际跑过的命令与结果
- 缺陷修复：在 `docs/specs/<date>-<fix>.md` 或 `AGENTS.md` 的变更说明中记录
- 长期回归追踪：在仓库 CI 的 artifacts 中保留（如 `test-results/`）
